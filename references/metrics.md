# 指标口径定义 · Metrics

这份文件只回答一个问题：**报告里的每个数字是怎么算出来的。**

任何一条结论都必须能在这里找到对应的计算规则。找不到规则的数字，不允许出现在报告里。

---

## 0. 数据基础

| 项 | 口径 |
|---|---|
| 数据来源 | 麦当劳中国 MCP `order-list` + `query-order` |
| 样本范围 | 官方返回的**近期**订单，**不是**全年完整历史 |
| 时间解释 | 订单时间字段不含时区，统一按 **UTC+8** 解释，**不做跨时区换算** |
| 金额单位 | 接口返回的是**元**（字符串，如 `"14.9"`）；内部统一折算为**分**计算，展示时换回**元** |
| 小计校验 | `subtotal_fen` 应 = Σ(`amount_fen` × `quantity`)；不一致即告警 |
| 实付校验 | `total_fen` 应 = `subtotal_fen` − `discount_fen`；不一致即告警 |

---

## 1. 时间热力（周 × 时段）

**时段划分**（左闭右开，按当日分钟数判定）：

| 时段 | 区间 |
|---|---|
| 深夜 | 00:00 – 05:59 |
| 早餐 | 06:00 – 10:29 |
| 午市 | 10:30 – 13:59 |
| 下午茶 | 14:00 – 16:59 |
| 晚市 | 17:00 – 20:59 |
| 夜宵 | 21:00 – 23:59 |

- 矩阵 = 7（周）× 6（时段），**格值 = 落在该格的订单数**
- 颜色深浅 = 格值 ÷ 全矩阵最大值，线性映射
- 星期行按 `datetime.weekday()`，周一为第 0 行

> **注意**：这是本次样本的时间分布，**不代表长期习惯**。

---

## 2. 月度节律

- 按自然月分组，统计当月订单数
- 柱高 = 当月订单数 ÷ 样本内最大月订单数
- **样本跨度不足两个月时，这一维没有意义，不要过度解读**

---

## 3. 点餐方式分布

五种归一口径：

| 归一名 | 含义 |
|---|---|
| 到店取餐 | 到店自取 |
| 麦乐送 | 外送配送 |
| 得来速 | 汽车餐厅车道取餐 |
| 堂食外带 | 堂食或打包外带 |
| 企业团餐 | 团餐助餐场景 |

- 占比 = 该方式订单数 ÷ 总订单数
- 无法判定的订单标为「未知」，**单独列出，不并入任何一种**

---

## 4. 品类结构

**这是启发式归类，不是麦当劳官方分类。** 按商品名称关键词匹配，命中即停：

| 品类 | 命中关键词（示例） |
|---|---|
| 早餐 | 麦满分、满福堡、热香饼、薯饼、粥、油条 |
| 汉堡 | 巨无霸、麦辣鸡腿汉堡、板烧、麦香鸡、吉士、安格斯、鳕鱼、堡 |
| 咖啡 | 麦咖啡、拿铁、美式、卡布、摩卡、澳白 |
| 冰品甜点 | 新地、麦旋风、圆筒、冰淇淋、圣代、派 |
| 小食 | 薯条、麦乐鸡、鸡块、鸡翅、香骨鸡、玉米杯 |
| 饮料 | 可乐、雪碧、芬达、橙汁、柠檬茶、豆浆 |

- 金额占比 = 该品类累计金额 ÷ 全部商品金额
- 未命中任何关键词 → 归「其他」
- **已知局限**：同一商品在不同门店可能有不同命名（"中薯条" / "薯条(中)"），
  归类会因此出现偏差。完整规则见 `scripts/footprint_aggregate.py` 的 `CATEGORY_RULES`。

## 5. 城市足迹

- **官方接口不返回门店经纬度**，因此不做地理坐标绘制，只做行政区划层级
- 城市来源有两条，**按优先级**：
  1. **门店地址文本**（`storeAddress`）—— 解析直辖市 /「XX省」/「XX市」/「XX区」
  2. **门店名前缀**（`storeName`）—— 地址里解析不出城市时兜底。
     门店名格式是「麦当劳 + 城市 + 店名 + 餐厅」，去掉「麦当劳」前缀后，
     用**内置城市表做最长前缀匹配**（约 180 个常见城市，先试 4 字、再 3 字、再 2 字）
- **实测：`storeAddress` 通常不含城市**，街道级地址如「东山街道玖力大厦1号楼1层101…」，
  所以第二条不是可选优化，而是主路径。
- 两条都拿不到 → **留空，不做猜测填充**；报告口径区会写明城市来源
- 解析不出城市的订单：**计入总额，但不计入城市维度**（报告会告警）
- 城市排序：订单数降序，同数则按金额降序

> 为什么不用"取前两个字"这种简单切法：城市名 2~4 字不定长，
> 「麦当劳哈尔滨中央大街餐厅」会被切成「哈尔」。宁可不认，也不能认错。

## 6. 优惠账本

> **维度已变更（2026-10-18）**：原设计是「麦金卡账本」，实测确认接口
> **不返回任何持卡 / 权益字段**（20 份真实返回全量搜索 card / 麦金 / 会员 / vip 零命中），
> 该维度无法支撑。同位置、同目的、但真实可算，改为优惠账本。

| 指标 | 算法 | 数据来源 |
|---|---|---|
| 折前原价 | Σ(订单 `totalAmount`) | query-order |
| 实际支付 | Σ(订单 `realTotalAmount`) | 两个接口都有 |
| 累计省下 | Σ(订单 `totalDiscountAmount`) | query-order |
| 节省比例 | 累计省下 ÷ 折前原价 | 推算 |
| 用券订单数 | 有 `couponList` 非空的订单数 | query-order |
| 券的贡献 | 按 `couponName` 汇总 `discountAmount` | query-order |
| 省钱最多的一单 | 单笔优惠金额最大的一单，附原价 / 实付 / 折算折扣 | query-order |

**自洽校验**：原价 − 省下 应当等于实际支付；券明细金额之和应当等于累计省下。
两者对不上就说明映射错了，脚本会告警。

> **不要把这个维度说成"卡值不值"**。它回答的是"省下的钱从哪来"，
> 而不是"月费有没有回本"——因为接口根本不给持卡信息。

## 7. 堂食 / 外带

| 指标 | 算法 |
|---|---|
| 分布 | 按 `takeWay`（`堂食` / `外带`）统计订单数与金额 |
| 与「点餐方式」的区别 | `beType` 说**怎么取餐**（到店/麦乐送/得来速/团餐），`takeWay` 说**在哪吃** |

> 实测 `beType` 常常全场只有一个取值（10 单全是「到店取餐」），
> 单靠它这一维度没有比较意义。报告在点餐方式下方补一行堂食/外带，并注明退化情况。

---

## 8. 样本量告警

| 样本量 | 等级 | 含义 |
|---|---|---|
| < 5 单 | error | 不足以支撑任何分布结论 |
| 5 – 14 单 | warn | 分布结论稳定性有限 |
| ≥ 15 单 | — | 正常输出 |

---

## 9. 口径变更约定

改口径时**只改 `scripts/footprint_aggregate.py` 顶部的常量区**，并在此处同步更新。
**不要让口径散落在多个文件里**——那会让"数字怎么来的"变得无法追溯。
